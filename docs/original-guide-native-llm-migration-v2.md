# 原著指导迁移方案 v2：复用原生填表与 LLM 模型逻辑召回

日期：2026-10-26。本文修订并优先于《原著指导-独立数据库唯一后端迁移设计.md》中冲突的内容。实现基线为 AlbusKen/shujuku main（0d9cc1a），fork 为 paff67/shujuku。

## 1. 用户已确定的边界

- 使用数据库的「LLM 模型逻辑召回」模式。不得启用交火模式、向量召回或自动回退到这些模式。
- 填表和召回都复用数据库现有完整流程，包括有效配置解析、上下文组装、模型调用、原生重试、解析及后处理；填表还包括原生提交与持久化。
- 填表和召回的基础提示词使用数据库中用户实际选中的配置，不是把默认提示词写死，也不是复制到角色卡后维护第二份。
- 原著指导特有的要求只保留必要的业务差异：纪要内容规范、原著上下文和截止点、轮回来源隔离、原著推进与 MVU。
- 禁止角色卡传入完整 messages 来替换数据库提示词；禁止另造一套 JSON/SQL 模型输出协议、解析器和模型重试循环。
- 旧纪要只用于迁移/导出；新数据、历史与快照由数据库管理。原著指导不再写 xz_memory_v1。

## 2. 已核对的代码与可行性

下列是当前源码事实，不等于线上验收通过。

| 需求 | 现有实现基础 | 判断与缺口 |
| --- | --- | --- |

## 3. 三类特殊要求如何实现

### 3.1 原有纪要提取要求：可实现，规则配置加提交约束

旧卡中实际存在：只追加纪要、不修改其他表；记录已发生事实；保留重要 NPC 原话并标明说话者；玩家直接引语每条纪要最多一句；区分正常亲密互动与主从压迫叙事；编码不重复；每段至少生成一条纪要。

处理方式：

1. 使用原生表模板建立/映射纪要表，字段与含义由数据库模板管理。旧字段 code/time/summary/text/dialogue 映射到实际表列，不强行假定运行时表名恒为 chronicle。
2. 语义要求写入本书纪要表说明/Note 或专用业务补充段，随数据库模板编辑、保存和导出；不替换用户已选填表主提示词。
3. 业务补充不包含旧 SQL 示例、thought/content 标签或旧响应格式指令，输出协议完全由原生模式决定。
4. 在原生解析后、提交前增加可复用的写入策略校验：本次自动提取只能写目标纪要表、允许的操作与列，不能越界修改其他表；人工编辑和明确重填任务使用各自策略，不全局禁止数据库编辑。
5. 每段至少一条只能绑定明确的原生填表批次/来源范围。不要把数据库合批强制误解成每个物理楼层都必须调用一次模型；需要逐段精度时用原生批次设置或扩展原生分段元数据。
6. 文本是否忠实、NPC 原话是否充分保留属于模型语义质量，不能宣称代码硬保证。可机械校验的来源、操作范围、重复编码和空结果则用代码校验。

### 3.2 原著相关性筛选：可实现，区分相关性与事实边界

旧卡召回以当前内容关联为主，并提供当前对话、人物背景和候选纪要；开局前情另有来源标记与修改保护。不能把整本原著未来剧情视为已发生纪要。

- 原著章节窗口、当前节点、在场人物、当前目标和本局偏离由卡生成结构化上下文，通过原生上下文构建器/受控模板变量接入数据库任务。
- 基础筛选方式、数量、时间展示、任务提示词继续使用数据库有效配置。旧卡的整套召回提示词不迁入、不覆盖。
- 仅当当前配置无法表达本书需要的“区分原著计划与本局事实”等差异时，添加可见、可编辑的本书补充规则段。补充段不改变原生返回格式。
- 原著未来事件可作为卡的推进参考，但不得混入“本局已发生纪要”候选。候选来源、节点截止点与可见性在发送模型前强制过滤，返回结果再次校验候选身份。
- 原著事件不是纯时间序列：不能只比较章节数字，必须使用卡的稳定节点/事件身份与分支状态；缺少对应关系时显式报错，不猜测截止点。
- 原著与本局冲突时保留来源区分，不让数据库自行改写原著推进状态或 MVU。

### 3.3 轮回记忆限制：可实现，但必须增加正式隔离能力

旧卡规则包括：本局与最多一个旧存档两路召回；旧档纪要在轮回时冻结；来源 revision 必须一致；派生存档禁止二次轮回；携带角色由独立 MVU 选择/初始化流程约束。

- 数据库正式快照保存冻结纪要、模板/列映射、来源身份和 schema/revision；只读锚点引用该快照。不能在召回时重新查询来源聊天的最新纪要。
- 用同一套原生 LLM 任务管线分别读取本局候选和冻结候选，结果带 sourceScope/snapshotId/stableRowId。相同 AM 编号不可跨来源混淆。
- 使用数据库有效召回提示词；原生模板变量在各自请求内解析为对应数据。不要把旧档数据覆盖到全局 currentJsonTableData 后再还原。
- 审查 SQL 模板、EJS、世界书、总结索引和任务中继等全部读取分支。PlotRequestContext 仅是基础；尚未验证的全局回读必须补成显式请求上下文，否则冻结召回不得宣称可用。
- 源档后续追加、改写、删除不影响冻结候选；只读快照不可作为填表目标。当前生成上下文与旧档候选分开建模，避免把旧对话伪装成当前正文。
- “携带谁”“派生档不得再次轮回”“轮回身份与普通同名人物分开”保留在卡的轮回/MVU 编排与数据库请求准入校验，不仅写在提示词中。
- 两路召回是一次生成任务中的两个来源，不是交火模式。共享一个取消/失效边界，最终只注入一次。

## 4. 提示词与配置的唯一归属

| 内容 | 唯一管理位置 |
| --- | --- |
| 填表基础提示词、模式及格式协议 | 数据库现有配置界面与解析器 |
| LLM 召回任务、提示词、数量、接口方案 | 数据库当前聊天有效配置 |
| 本书纪要业务规范 | 数据库本书模板说明/业务补充段 |
| 原著节点、章节窗口、当前人物等动态输入 | 原著指导提供，数据库受控变量解析 |
| 原著推进规则、MVU、轮回角色选择与入场说明 | 原著指导保留 |
| 冻结快照、候选范围、来源检查、写权限 | 数据库代码强制执行 |

角色卡中的旧纪要填写/召回提示词编辑入口改成打开数据库对应配置，不再保存第二份。旧配置提供只读导出或选择性提取业务规则，不自动整段覆盖数据库提示词。数据库用户修改配置后，下次请求使用新 revision；已运行请求冻结原配置，失效规则明确。

## 5. 原生流程接入顺序

### A. 撤掉并行实现方向

- 审查 src/memory/memory-request.ts、memory-protocol.js、memory-crossfire.ts 及 acu-memory-backend.ts：移除其承担的独立模型调用/重试/填表解析/召回解析职责。
- scope、稳定 ID 和结果映射可以保留，但不得形成另一套正式数据源。
- 请求接口传入操作意图、来源范围、目标表和业务上下文；不再由卡提交完整 messages 或私有 fillPreset/recallPreset 去绕开数据库配置。

### B. 填表接入

从现有触发器、调度器到 executeCardUpdateCore_ACU 的真实调用链确定公共 service adapter。保留其忙状态、来源快照、批处理、取消、失败恢复与提交后工作。卡的补齐/手动填写变成该入口的调用；自动填表仅保留一个调度所有者。新增业务策略验证挂在原生提交之前，验证错误走原生可恢复失败路径。

### C. LLM 逻辑召回接入

通过当前聊天模式设置选择 llm，通过原生预设解析和 runPlotTasksRuntime_ACU 所在完整调用链运行。保留原生输出解析、任务依赖、重试及后处理。需要结构化结果时从原生解析结果导出，不增加另一套 LLM 输出协议。

数据库的“剧情推进”是该调用链的模块名，不能全关。为本书新增明确的“仅导出召回结果、由宿主统一注入”执行出口（待实现），保留原生任务语义与用户选中提示词，不自动删除用户任务。若当前任务预设还输出剧情建议，必须区分召回与建议；若无法可靠区分则提示配置不兼容，不直接注入所有原始文本。

卡继续负责原著推进。原生自动 hook 与卡的主动请求选定唯一入口，同一生成身份合并任务、只注入一次；必须核对宿主真正的取消接口，不能把事件回调抛错当作停止正文生成。

### D. 存档与轮回

接入数据库正式快照/恢复流程，并增加冻结请求上下文读取能力。完整存档仍由卡编排聊天、世界书、MVU 与数据库快照；跨多个宿主保存不是原子事务，使用分阶段回执与可恢复状态。先验证正常快照读写，再实现轮回只读锚点与两来源召回。

### E. 交火退出与兼容

不要求交火能力，不建立向量索引、不调用 embedding/reranker、不保留交火预设为必填项。旧存档中 crossfire 字段只在旧包解析兼容层接收并跳过，不作为新数据正确性条件；不为清理旧字段而改写原始存档。新快照只存需要的纪要/结构/来源数据。

## 6. 必要验证与交付边界

只做定向验证，不重复全量测试：

1. 数据库界面修改填表/召回提示词，真实入口下一次组装的消息随之变化；卡旧提示词不再参与。
2. 填表与召回实际调用原生编排器；不出现第二套模型重试或重复自动任务。
3. 模式为 llm，交火/向量调用次数为零；召回结果只注入一次。
4. 填表越界操作被原生提交前校验拦截；本书普通人工编辑不受误伤。
5. 原著未来事实不进入已发生纪要；本局与轮回同编号可区分；来源档变化不改变冻结候选。
6. 切聊天、改 swipe、换配置、取消任务与保存失败不会跨 scope 写入或部分注入。
7. 定向测试、类型检查、必要构建及 diff 检查完成后报告；真实模型语义和实际宿主保存/重载须单独验收，未执行则明确标注。

## 7. 当前结论

纪要业务要求可通过原生模板与有限策略扩展承载；原著相关性可通过原生提示词配置和受控上下文承载；轮回需要新增冻结来源隔离能力，但可以复用同一原生 LLM 管线。三项均不要求交火模式，也不要求保留旧卡的完整填表/召回提示词。当前结论来自源码检查，尚未完成代码改造与宿主验收。
